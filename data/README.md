# Dataset card

This repository has **no real dataset** and downloads nothing. Every experiment runs on
**synthetic** scheduler workloads that the code generates from integer seeds, on the fly, each
time a simulator episode starts. This folder holds one helper script that writes such a workload
to a CSV file so that it can be inspected; it holds no data, and generated files are git-ignored
and never committed.

| Dataset | Role | In the repository | Results |
|---|---|---|---|
| [Synthetic scheduler workloads](#synthetic-scheduler-workloads) | the only workloads of the scheduling benchmark | generator code and an inspection script | `[Reproduced]`, see [RESULTS.md](../experiments/results/RESULTS.md) |

No real medical, financial or personal records, no real job traces and no measurements of a real
machine are in this repository. Nothing needs to be downloaded before the tests, the smoke run or
the full benchmark can run.

## Synthetic scheduler workloads

### Summary

The scheduling benchmark runs on synthetic workloads only. There is no real scheduling dataset in
this repository and none is claimed. Every distribution below is `[Assumption — not in paper]`:
it was written down by this repository so that the benchmark can be run and repeated.

A **workload** here is the list of tasks that one simulator episode schedules. A **task** has an
arrival time, a type (one of the three execution patterns), an alternating sequence of CPU bursts
and I/O waits, a memory footprint, a static priority level and a deadline. A **load profile**
(light, medium or heavy) sets the target CPU utilisation, that is, how densely tasks arrive
relative to the CPU work they bring.

| Fact | Value |
|---|---|
| Kind | Synthetic, generated by code from a seed; no file is stored |
| Generator | `generate_workload` in [src/scheduler/tasks.py](../src/scheduler/tasks.py) |
| Settings | the `workload:` section of [configs/scheduler_ddqn.yaml](../configs/scheduler_ddqn.yaml), listed in full below |
| Task types | CPU-bound, memory-bound, I/O-bound; with the [LLM-style workload profile](#the-llm-style-workload-profile): inference requests, fine-tuning jobs |
| Load profiles | light, medium, heavy (target CPU utilisation per profile in the config) `[Assumption — not in paper]` |
| Units | time in milliseconds (ms), memory in megabytes (MB) |
| Determinism | the same config, load profile and seed always give the same workload |
| Licence | the generator is code of this repository and carries its licence (Apache License 2.0, see [LICENSE](../LICENSE)); generated workloads are not distributed |

### How it is generated

Each simulator episode generates its workload on the fly from a seed; nothing is generated in
advance, and the benchmark commands (`make smoke`, `make scheduler`) need no data step. To write
one workload to CSV so that you can look at it, run from the repository root:

```bash
python data/synthetic/generate_scheduler_workload.py --load heavy --seed 100 \
    --out experiments/results/runs/workload_heavy_100.csv
```

The script takes `--load` (`light`, `medium` or `heavy`), `--seed` (an integer) and `--out` (the
CSV path), and optionally `--config` (default `configs/scheduler_ddqn.yaml`), `--smoke` (merge the
smaller smoke-run settings of the config) and `--set key=value` (override one config key, for
example `--set workload.n_tasks_max=80`). It logs the number of tasks, their total CPU demand and
the span of their arrival times. Writing the CSV under `experiments/results/runs/` keeps it out of
version control; `data/synthetic/*.csv` is git-ignored as well.

The generator ([generate_scheduler_workload.py](synthetic/generate_scheduler_workload.py) calls
`generate_workload`) draws, for each episode, a number of tasks between the configured minimum and
maximum. For each task it draws a type from a weighted mixture of the three patterns; a total CPU
demand from a log-normal distribution clipped to a per-type range; a number of I/O operations,
which splits the demand into one more CPU burst than there are I/O waits; uniform I/O waits; a
uniform memory footprint (the memory-bound type uses footprints large enough to make the simulated
machine thrash when several run together); and a priority level. Inter-arrival times are
exponential with mean equal to the workload's mean CPU demand divided by the target CPU
utilisation of the load profile, so the light, medium and heavy profiles differ only in how
densely tasks arrive. The first task arrives at time zero. Each task's deadline is its arrival plus
a per-type multiple of its own CPU and I/O time plus a fixed slack. Task attributes and arrival
times come from two separate random streams derived from the seed, so changing the load profile
changes the arrival times and leaves the tasks themselves unchanged. The exact values are in the
config listing below.

### The LLM-style workload profile

The LLM-style workload profile is a second synthetic workload definition. Its tasks are of two
classes instead of three: short, latency-sensitive **inference requests** and long, memory-heavy
**fine-tuning jobs**, sharing one simulated node. No language model is run: the profile is a
synthetic task mix shaped like the work of an LLM platform, and none of its values was measured
on an LLM system. The simulator's single processor and its memory budget stand in for that node.

It is generated by the same generator, from
[configs/scheduler_llm_workload.yaml](../configs/scheduler_llm_workload.yaml). That file inherits
every setting of `configs/scheduler_ddqn.yaml` (machine, load profiles, task counts, deadline
slack, seeds and so on) and replaces only the task classes and their priority weights: inference
requests are drawn on the two upper priority levels, fine-tuning jobs on the two lower ones. The
deadline, arrival and burst rules described above apply unchanged, with the per-class values of
the profile. The study that uses it is section 4 of
[RESULTS.md](../experiments/results/RESULTS.md).

### Preprocessing

None. The simulator normalises the agent's observation as set in the `observation:` section of the
same config; the baselines read the task fields directly.

### Splits

There is no fixed train / test file. The split is made by seeds:

- **Reporting seeds** 0–4 produce every `[Reproduced]` value. For each reporting seed the
  benchmark trains one agent and generates a fixed set of evaluation workloads per load profile.
- **Training workloads** and **evaluation workloads** of a seed come from separate child seeds
  (one labelled for training episodes, one for evaluation), so the agent never trains on a
  workload it is evaluated on. The load profile of each training episode is drawn at random.
- **Every method** (the four baselines, SRTF, the guarded agent and the agent with its override
  rules off) is evaluated on exactly the same evaluation workloads, so differences between methods
  are paired. The `workload_seed` column of `raw_episodes.csv` in the reference run records which
  workload each row used.
- **Development seeds** are 100 and above. Settings were chosen on them; the reporting seeds were
  used once, for the reference run.

### Privacy note

Synthetic numbers only; nothing describes a real machine, user or job. The same holds for the
LLM-style workload profile: it is synthetic, and it contains no real request, prompt, user or
trace data.

### Claims this dataset can and cannot support

Results support comparisons between schedulers on this simulator and these workload
distributions. They do not support claims about a real operating system, real job traces,
multi-core machines or cluster schedulers.

The LLM-style workload profile supports statements about scheduling policies on a mix of this
shape — many short urgent tasks next to a few long, memory-heavy ones — in this simulator. It
supports no statement about a language model, a serving system or real traffic.

### Known limitations

- Every distribution is an assumption of this repository; none is fitted to a real trace.
- The generator has no temporal correlation, no bursts of arrivals beyond the Poisson process and
  no task dependencies.
- The exact current burst length is available to every scheduler, which a real system would have
  to estimate; this makes every absolute result optimistic.
- The memory-bound type is tuned so that a few such tasks together exceed the simulated memory and
  trigger the thrashing penalty. Results under heavy load depend strongly on that choice.
- A workload has a few dozen tasks (see `n_tasks_min` and `n_tasks_max`), so each episode is
  short and per-workload results vary a lot; the tail analysis in RESULTS.md shows how much.
- The values of the LLM-style workload profile are hand-chosen to give the mix its shape; they
  are not fitted to a trace. Its times are simulator milliseconds: they keep the ratio between a
  request and a job, not the absolute durations of a production system. One processor and one
  memory budget stand in for a node, with no batching of requests and no model-loading cost.

### Using your own workloads

There is no trace loader. To run the benchmark on other workloads you can either change the
`workload:` section of the config (or pass `--set` overrides to the benchmark), or write a loader
that produces the `Task` objects of `src/scheduler/tasks.py` and pass them to the environment,
which accepts a ready-made workload in `reset(options={"workload": ...})`. Any real trace you use
this way stays outside the repository; do not commit it.

To study other task classes, define a workload profile: a config with `base_config:
scheduler_ddqn.yaml`, `replace_keys: [workload.task_types]` and its own `workload.task_types`, as
the LLM-style workload profile does. The classes are the keys of `workload.task_types`, so no
code change is needed. The steps are in the README recipe "Recipe: define a workload profile"
([README](../README.md)).
